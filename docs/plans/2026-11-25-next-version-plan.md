## 0. 결론

1. 룰 쪽 루프(교정 → 룰 → 주입)는 돌고 있다. 고장은 **범위가 저장 시점에 사라지는 것**이고(초안 진단과 같음), 그 결과 홈에서 시작한 세션은 예산을 넘겨 룰이 순위로 잘린다.
2. 솔루션 쪽 루프는 **저장까지만 돌고 그 뒤가 전부 끊겨 있다.** 20일 동안 257개가 새로 쌓였는데, 승급에 필요한 신호 세 가지(재추출·코드 반영·세션 수)를 올리는 경로가 실제 추출 경로에 연결돼 있지 않다. 검증 0건은 데이터 부족이 아니라 구조다.

4. 그래서 다음 버전은 초안의 "범위" 한 갈래가 아니라 세 갈래다: **(S) 범위와 위치**, **(K) 솔루션 루프 출혈 중지**, **(M) 정직한 계측**. 새 기능(발동 조건, 꿈꾸기, 이식 확장)은 이 셋 위에 얹어야 하므로 0.9 이후로 둔다.

숫자(초안 F3 을 이것으로 고친다):
- 팀 리드 실측: 11-05 이후 `correction-record` 호출 36건(중복 제거), `this_project_only=true` 27건 **전부 전역 저장**, 그중 17건은 호출 시점 폴더가 git 저장소 안.
- 이 조사의 교차 확인 [데이터]: 11-05 이후 직접 교정 근거 파일 32개. 32개 모두 **홈에서 시작한 세션**이고, 교정 시점의 폴더는 git 저장소 안 19 · git 아닌 폴더 8 · 홈 5. 근거 파일에 `projects` 가 있는 것은 직접 71건 중 0.
- 추론 교정(초안 F5)의 집계 필터: `raw_payload.auto_mined === true` 355건 중 `generality === 'project'` 25건, 그중 `projects` 저장 0건. `generality` 가 없는 0.7.0 이전 305건은 이 25에 들어 있지 않다(판정 자체가 없던 시기). `general` 은 25건.
- 32건을 제품으로 묶으면 [데이터]: **한 제품이 23건(72%)** 이고 그 23건이 저장소 2개(11건·7건)와 git 아닌 조사 폴더(5건)에 흩어져 있다. 나머지는 다른 저장소 1 · Claude 메모리 폴더 2 · 미등록 폴더 1 · 홈 5. 지금의 "저장소 이름 = 범위"로는 호출 시점 폴더를 정확히 써도 같은 제품 룰이 키 2개와 무범위로 갈라진다.
- 초안 F1 의 "52개 중 최소 25개"는 정책 문장과 계기(trigger)에 특정 제품의 이름·도메인 용어 정규식(공개 문서라 생략) 를 댄 하한이다(팀 리드 집계).
- 격리 세션 재현 [실측]: 비-git 폴더에서 시작 → `cd` 로 git 저장소 이동 → `this_project_only=true` 로 호출. 훅 입력의 `cwd` 는 저장소였는데 응답은 "not inside a git project — recorded as global" 이었다.
- 세션 기록 51개 중 21개(41%)가 홈에서 시작했다 [데이터]. 이 사용 방식에서는 "시작 폴더 = 작업 위치" 가정이 거의 맞지 않는다.
- 따라서 호출 시점 폴더를 쓰는 것만으로는 32건 중 19건만 풀리고 그것도 키가 갈라진다. 폴더를 한 키로 묶는 장치와, "모름"을 전역과 구분해 담을 자리가 같이 필요하다.

### 2.2 솔루션이 후보에 머무는 이유 — 구조다

승급 조건: 후보 → 검증은 "(코드 반영 4회 이상이고 세션 3곳 이상) 또는 재추출 2회 이상", 부정 근거 0, 그리고 최소 경과 14일 (`src/engine/compound-lifecycle.ts:106-117`, `:22-27`) [코드]. 세 신호가 각각 막혀 있다.

| 신호 | 왜 안 오르나 | 근거 |
|---|---|---|
| 재추출 | Haiku 추출 경로는 `forgen compound --solution` 을 실행하고(`auto-compound-runner.ts:339`), 같은 이름이 있으면 **건너뛰고 끝난다**(`compound-loop.ts:72-95`). 재추출 카운터를 올리는 코드는 git diff 추출기(`compound-extractor.ts:255`)와 가져오기(`compound-share.ts:517`)에만 있다 | [코드] 재추출 0/297 [데이터] |
| 코드 반영 | 주입된 솔루션의 identifier 가 15분 안에 쓰인 코드에 나오거나, 6자 이상 태그 2개가 코드에 나와야 한다(`pre-tool-use.ts:337-349`). 추출 프롬프트는 제목에 파일·함수 이름을 쓰지 말라고 하고(`auto-compound-runner.ts:287`) identifier 는 제목·본문의 영문 식별자에서만 뽑는다(`compound-loop.ts:141-155`) | [코드] identifier 가 빈 솔루션 279/297 [데이터] |
| 세션 수 | 코드 반영이 처음 잡힐 때만 오른다(`pre-tool-use.ts:354-358`). 그 밖의 경로는 MCP 읽기인데 읽을 때마다 반영과 세션을 함께 +1 한다(`mcp/solution-reader.ts:306-311`) | [코드] 세션 수 1 이상 2/297 [데이터] |

| 주입 자체 | 위 신호의 전제인 주입이 30일 16건 | [데이터] |

덧붙여 확인한 것:
- Haiku 가 뽑은 솔루션이 **사람이 쓴 것으로 표시된다.** 수동 추가 경로를 그대로 타서 `source: 'manual'` 이 된다(`compound-loop.ts:631`, `:172`). `extractedBy: manual` 279개 [데이터]. 자동 추출만 대상으로 하는 정리 규칙(`solution-habit.ts:5-17`)이 이들을 비켜 간다.
- README 는 솔루션이 experiment(0.30)에서 시작한다고 하지만 이 경로는 candidate(0.5)로 만든다(`compound-loop.ts:162-163`) [코드].

- 중복 방지용으로 프롬프트에 주는 기존 이름은 폴더 목록의 뒤 30개다(`auto-compound-runner.ts:299`). 최근 30개가 아니라 정렬상 뒤쪽 30개이고 297개 중 일부일 뿐이다 [코드].
- 부정 근거를 올리는 경로는 도구 실패 귀속 하나(`post-tool-handlers.ts:120`)이고 0/297. **틀린 솔루션이 내려갈 길이 사실상 없다** [코드·데이터].

### 2.3 회수가 통과하지 못하는 이유 — 게이트는 설계대로, 근거가 낡았다

- 30일 판정 1,959건(상위 5 후보씩 기록, 여기에 구기록 90건을 더하면 화면의 2,049): 관련도 미달 1,825 · 이미 주입 103 · 태그 부족 17 · 통과 14 [데이터]. 프롬프트 단위로 묶으면 453개 중 통과가 있는 것 13개, 후보 5개가 모두 관련도 미달인 것 355개.
- 관련도 미달 판정의 88%(1,313/1,486)는 **맞은 태그가 1개**다. 프롬프트별 최고 후보의 관련도는 62%가 0.2 미만이다 [데이터]. 즉 대부분은 흔한 단어 하나로 걸린 후보를 게이트가 막은 것이고, 이는 2026-04-21 에 의도한 동작이다(`solution-injector.ts:60-90`, `relevance-gate.ts`) [코드]. **버그가 아니다.**

### 3.2 룰·솔루션·스킬·프로필의 역할

| 종류 | 무엇 | 언제 나타나나 | 강제 |
|---|---|---|---|
| 룰 | 내가 일하는 방식(선호·금지). "항상/하지 마라" | 범위 안에서 항상 | 결정적 탐지기가 있으면 차단, 아니면 자문 |
| 솔루션 | 상황 지식. "이런 상황에서는 이렇게" | 그 상황일 때만 | 없음 |

지금 "룰이어야 할 것"과 "솔루션이어야 할 것"이 추출 단계에서 따로 뽑히고(Haiku 호출 3회 중 2회) 서로 모른다. 목표는 분류 기준 하나다: **상황 조건 없이 늘 적용되면 룰, 상황 조건이 있으면 솔루션.** 0.9 에서 추출 단계를 합친다.

### 3.3 승격 경로 하나로

```
관측 1회        →  후보      (주입 안 함. 룰은 0.7.0 부터 이렇게 동작)
```

## 4. 0.8.0 범위

원칙은 11-17 문서 §0 을 그대로 쓴다: 해로운 동작을 먼저 멈춘다, 기존 데이터는 자동으로 바꾸지 않는다(미리보기 → 스냅샷 → 적용 → 되돌리기), 새 필드는 선택 필드로만 더한다.

### S1. 호출 시점의 위치를 훅이 붙인다 + 해석기 하나

- **문제**: §2.1. 위치를 묻는 곳마다 다른 값을 쓴다(MCP 는 시작 폴더, 러너는 인자, 훅은 입력의 `cwd`). MCP 프로세스는 자기가 어느 세션에 속하는지 알 길이 없다: 폴더는 시작 때 한 번 고정되고(`server.ts:18-20`), `session_id` 는 모델이 넘기는 값이며(`tools.ts:333`) 모델은 자기 ID 를 확실히 모른다(`evidence-processor.ts:47` 주석). `FORGEN_SESSION_ID` 는 래퍼로 띄웠을 때만 있다(`tools.ts:348`).
- **실측 (Claude Code 2.1.332, 격리 세션)**
  - PreToolUse·PostToolUse 훅은 MCP 도구 호출에도 온다. 입력에 실제 `session_id`, 그 시점의 `cwd`(Bash `cd` 뒤 값), `tool_use_id`, `tool_input`, `mcp_server` 가 있고, PostToolUse 에는 `tool_response`(근거 ID 포함)도 있다.
  - forgen 훅이 없는 세션에서 모델은 `session_id` 에 자기 ID 를 넣지 못했다(모른다고 답함). 근거는 그 값 그대로 저장됐다.
  - PreToolUse 훅이 `hookSpecificOutput.updatedInput` 으로 `session_id` 와 `message` 를 바꿔 보내자 MCP 가 **바뀐 값**을 받았다(저장된 근거의 세션 ID = 실제 세션 ID).
  - 실데이터에서는 11-05 이후 직접 교정 32건의 세션 ID 가 모두 실제 대화 기록과 맞았다. 다만 이건 그 세션들에서 맞았다는 관찰일 뿐 보장이 아니다.
- **설계**
  1. **1순위(Claude)**: forgen 의 PreToolUse 훅이 도구 이름이 `…__correction-record` 인 호출을 보면 `updatedInput` 으로 `session_id` 를 실제 값으로 덮고 `origin: {cwd, tool_use_id}` 를 붙인다. MCP 는 `origin.cwd` 로 프로젝트 키를 구한다. 세션이 몇 개 떠 있든 호출마다 그 세션의 값이 오므로 **동시 세션 문제가 없다.**
  2. **2순위**: 훅이 `origin` 을 못 붙인 호출(훅 미설치·비활성, 호스트가 지원 안 함)은 세션 파일로 푼다. 훅(UserPromptSubmit·PreToolUse·PostToolUse)이 `cwd` 변화를 `state/session-context/<세션>.json` 에 적어 두고(현재 폴더, 프로젝트 키, 프로젝트별 턴 수, 이미 주입한 프로젝트), MCP 는 모델이 준 `session_id` 로 그 파일을 찾는다. 못 찾으면 추측하지 않고 미정(S2). "가장 최근 세션" 같은 추측은 하지 않는다.
  3. `resolveWorkContext()` 하나를 MCP·러너·훅이 쓴다. 결과는 `{kind: 'project', key} | {kind: 'none'}` 과 판정 경로 `via`(`hook-input` / `session-file` / `process-cwd`).
  4. 러너(추론 교정)는 호출이 아니라 세션 단위라 세션 파일의 프로젝트별 턴 수를 쓴다. 한 프로젝트가 80% 이상이면 그 키, 아니면 미정.
  5. 모든 근거에 `origin: {cwd, project, via, host}` 를 기록한다. 범위 판단과 별개인 사실 기록이다.
  6. 세션 파일은 S5(전환 주입)에도 쓰이므로 1순위가 되더라도 만든다.
- **바꿀 파일**: `src/hooks/pre-tool-use.ts`(보강 출력 — 이 훅의 stdout JSON 1개에 합친다), `src/hooks/shared/hook-response.ts`(`updatedInput` 을 담는 응답 함수 추가), 신규 `src/core/session-context.ts`, `src/store/rule-scope.ts`, `src/mcp/tools.ts:333-400`(선택 입력 `origin`), `src/mcp/server.ts:18-20`, `src/core/auto-compound-runner.ts:435-439`, `src/hooks/post-tool-use.ts`·UserPromptSubmit 진입 훅, `src/core/state-gc.ts`(세션 파일 정리 대상).
- **데이터**: 근거 `raw_payload.origin`(선택). 이전 없음. 0.7.2 가 모르는 필드가 든 룰을 그대로 읽는 것은 확인했다 [실측, §4.3].
- **테스트**: 홈 시작 → 저장소 이동 → 교정, 저장소 시작, worktree, **동시 세션 2개가 서로 다른 저장소**, 모델이 틀린 세션 ID 를 넘김, 훅 없음(2순위), 세션 파일 없음(미정). 각 경우의 기대 `via`.
- **아직 모르는 것 [미확인]**
  - `updatedInput` 으로 **스키마에 없던 키**를 더하는 것(실측은 기존 키 두 개를 바꾼 것). 입력 스키마에 선택 필드 `origin` 을 추가해 두고 확인한다.
  - PreToolUse 훅이 여러 개(다른 플러그인 포함) `updatedInput` 을 낼 때 어느 것이 이기는가. 매트릭스의 "다른 플러그인 공존" 칸에서 확인한다.

- **데이터**: 새 파일 하나. 지우면 지금 동작으로 돌아간다.
- **테스트**: 중첩 경로, 심링크, 없는 경로, 별칭 충돌, 등록부 손상 시 git 으로 폴백.

### K1. 추출: 0개가 기본, 원문 인용 필수

- **문제**: 실행의 56%가 상한 3개를 채운다. 20일에 257개. 근거가 대화 어디인지 남지 않는다.
- **러너 입력에 무엇이 있나 [코드]**: 요약에는 사용자 발화와 어시스턴트 발화의 **글**만 들어간다. 도구 호출과 도구 결과는 빠진다(`src/core/transcript-summary.ts:24-33`, `:91-104`). 어시스턴트 발화는 길이 상한으로 잘려 들어간다(`:255`). 즉 도구 출력을 인용하라고 해도 추출 모델은 그것을 본 적이 없다.
- **설계**: 프롬프트를 "다시 쓸 교훈이 있으면 … 없으면 없다고 답하라"로 바꾸고 각 항목에 **입력에 있는 원문 인용**과 그 종류를 받는다.
  - `user`: 사용자 발화 인용 — 교정·판단 기준에서 나온 교훈
  - `assistant`: 어시스턴트 발화 인용 — 작업 중 오류·실패로 알아낸 기술 교훈(어시스턴트가 "원인은 …였다"고 적은 대목). 사용자가 말하지 않은 교훈이 버려지지 않게 하는 길이다.
  인용이 요약 입력에 실제로 있는지 정규화 후 부분 문자열로 기계 검사하고, 없으면 저장하지 않는다. 인용·종류·세션 ID 를 솔루션에 남긴다(`grounding: user | assistant`). 종류는 0.8.0 에서 표시만 하고 순위에 쓰지 않는다. 내용에 대한 금지 규칙은 더 쌓지 않는다.
- **한계**: `assistant` 인용은 어시스턴트 자신의 말이라 틀린 결론도 통과한다. 인용 검사는 "지어내지 않았다"만 보장하고 "맞다"는 보장하지 않는다. 도구 출력(오류 메시지 원문)을 근거로 쓰려면 요약에 도구 결과 발췌를 넣어야 하는데, 이는 전송 범위(ADR-019 의 안내 문구)와 입력 예산을 바꾸므로 0.9 에서 따로 정한다.
- **바꿀 파일**: `src/core/auto-compound-runner.ts:280-345`, `src/engine/compound-loop.ts`(출처 인자), `src/engine/solution-format.ts`(선택 필드 `grounding`).
- **테스트**: 인용 없는 출력 → 저장 0, 인용이 입력에 없음 → 저장 0, 공백·문장부호만 다른 인용 통과, 종류별(user/assistant) 저장.

### K2. 재관측을 기록한다 — 검증은 아니다

- **문제**: 같은 교훈이 다시 추출되면 조용히 버려진다. 승급 경로 B(재추출 2회)가 죽어 있다.
- **재관측의 뜻**: 두 세션에서 다시 나왔다는 것은 **자주 나온다**는 뜻이지 **맞다**는 뜻이 아니다. 같은 추출기가 같은 오류를 두 번 낼 수 있다. 그래서 0.8.0 은 재관측을 연결하되 그것만으로 `verified` 를 주지 않는다.
- **`verified` 의 뜻을 이렇게 정한다**: (재관측: 서로 다른 세션 2곳 이상) **그리고** (확인: 오너가 승인함 — 오너 결정으로 사용 판정은 확인을 대신하지 않는다). 사용 판정(M3)은 0.8.0 에서 기록만 하므로 **0.8.0 의 확인 경로는 오너 승인 하나**다. '틀렸다' 판정이 쌓이면 부정 근거로 올려 내리는 것도 M3 일치율을 본 뒤 0.9 에서 켠다.
- **0.8.0 에서 `verified` 가 바꾸는 것 [코드]**: 주입 게이트 임계는 상태가 아니라 fitness 로 정해지므로 **통과 여부는 달라지지 않는다**(`solution-injector.ts:641-646`). 달라지는 것은 (1) 순위에 쓰는 confidence 0.55 → 0.75(`compound-lifecycle.ts:62-76`, `solution-matcher.ts:98-99`), (2) 스킬 승격 자격(`skill-promoter.ts:39`), (3) 낡음 기한 90 → 120일. 즉 0.8.0 에서 verified 는 "더 세게 주입"이 아니라 "오너가 본 것"이라는 표시이고 스킬의 원료다.
- **설계**
  1. 저장 직전에 기존 솔루션과 비교한다(이름 일치, 또는 기존 `contentSimilarity` 와 태그 겹침이 임계 이상). 같으면 새 파일을 만들지 않고 기존 솔루션에 근거 세션 ID 를 더하고(선택 필드 `evidence_sessions`, 최대 20개), **이전에 없던 세션일 때만** 재추출 +1. 같은 세션의 증분 추출은 세지 않는다.
  2. 후보 → 검증의 자동 승급 경로 A(반영+세션)와 B(재추출 2회), 둘 다 끈다(`compound-lifecycle.ts:108-117`). 카운터를 연결하는 순간 이 경로가 "두 번 나옴 = 검증"으로 동작하기 시작하기 때문이다. 대신 재관측된 솔루션은 `forgen compound review` 대기 목록에 오르고 오너가 승인하면 verified 가 된다(기존 `compound --verify` 재사용). 세션 시작 안내는 대기 3개 이상일 때 하루 1회.

## 6. 복리가 실제로 생기는지 증명

### 6.1 무엇을 주장할 것인가

"쓸수록 같은 교정을 덜 하게 된다." 이 한 문장만 증명 대상으로 삼는다. 시간 절약, 품질 향상은 주장하지 않는다.

### 6.2 세 층

| 층 | 방법 | 답하는 질문 | 인과 |
|---|---|---|---|
| L1 상시 계측 (0.8) | M2 의 3분류, 사용자 턴 100개당 직접 교정 수, 범위 오염(주입 룰 중 현재 범위 밖 비율), 세션당 주입 글자 수 | 루프가 어디서 새는가 | 주장 안 함 |
| L2 재생 비교 (0.10) | 과거의 실제 교정 지점을 과제로 쓴다. 교정 직전까지의 대화를 주고 (가) 그 룰이 주입된 상태와 (나) 빠진 상태에서 모델의 다음 행동을 받아, 오너가 교정했던 행동이 다시 나오는지 판정 | 룰 주입이 그 행동을 바꾸는가 | 있음 (같은 입력, 룰 유무만 다름) |
| L3 실사용 보류 (선택) | 세션마다 무작위로 일부 자문 룰을 빼고 재발 차이를 본다 | 실사용에서도 그런가 | 있음. 단 아래 한계 |

L3 의 한계를 숫자로: 직접 교정은 20일에 32건이다. 룰의 10%를 빼면 보류된 룰에서 나올 재발은 한 달에 몇 건 수준이라 통계적으로 판정할 수 없다. 오너가 같은 교정을 일부러 다시 하게 되는 비용도 있다. 그래서 기본은 L1 + L2 이고 L3 은 오너 결정으로 둔다(§8 Q3).

### 6.3 거짓 양성 방지

1. **사전 등록**: L2 를 돌리기 전에 과제 선정 기준, 판정 질문, 합격 기준을 문서로 고정한다. 결과를 본 뒤 기준을 바꾸지 않는다.
2. **분모는 기회**: 재발률의 분모는 달력 기간이 아니라 직접 교정 수와 사용자 턴 수다. 일을 안 한 주에 교정이 줄어든 것을 개선으로 읽지 않는다.
3. **교정 감소 ≠ 효과**: 교정이 줄어도 그것만으로는 아무것도 주장하지 않는다(2026-07-20 철회의 원인). 주장은 L2 의 룰 유무 차이에서만 한다.
4. **"같은 뜻" 판정 검수**: 3분류 표본 30건을 오너가 보고 일치율을 적는다. 80% 미만이면 숫자를 화면에 "참고"로만 표시한다.
5. **표본 하한**: L2 는 과제 30개 이상, 과제마다 3회 반복. 그보다 적으면 "판정 불가"로 보고한다.
6. **판정자 분리**: L2 판정 모델은 과제를 만든 추출 모델과 다른 모델을 쓰고, 어느 쪽이 룰 있는 응답인지 가린다.
7. **스스로 올리는 신호 금지**: 주입 횟수, 모델이 읽은 횟수는 검증 근거가 아니다. MCP 읽기가 반영과 세션을 함께 올리는 것(`solution-reader.ts:306-311`)은 0.9 의 원장 통합 때 근거에서 뺀다.
8. **공개 벤치 점수는 근거로 쓰지 않는다**(초안과 같음).

### 8.1 오너 결정 (2026-11-25)

| 항목 | 결정 |
|---|---|
| Q1 0.8.0 범위 | S + K + M 전부. S1~S3 먼저 |
| 솔루션 승격(새 질문) | **항상 오너 승인** (추천안 "승인으로 시작, 뒤에 자동" 대신) |
| Q3 효과 증명 | 상시 계측 + 과거 교정 재생 비교 |
| Q4 표면 축소 | 0.8.0 동결 표시, 0.9 제거 |
| Q2 범위 모델 | 오너에게 따로 묻지 않음. 추천안(2단계 + 키 등록부)을 기본값으로 둔다 |

"항상 승인"이 복리를 막지 않게 하는 장치(K2 에 포함):
1. 승인은 묶음으로: 같은 뜻을 합쳐 한 번에 최대 5건, 근거 인용과 함께. 기존 안내 주기(하루 1회)를 넘지 않는다.
2. 승인 전 후보도 지금처럼 게이트를 통과하면 주입된다(강도만 낮음). 승인이 밀려도 회수는 멈추지 않는다.
3. 승인하지 않은 후보는 새 근거가 없으면 기존 낡음 기한에 내려간다. 자동 검증은 없다.
4. 승인 대기 수·대기 일수를 `status` 에 표시한다.

구현 전 확인: verified → mature 의 자동 경로도 같은 결정에 걸리는지. 문자대로면 끈다(기본값).

구현(0.8.0 3단계)에서 정한 것:
- 자동 승급은 experiment → candidate 만. candidate → verified, verified → mature 는 자동으로 일어나지 않는다.
- 오너가 직접 치는 `forgen compound --verify <name>` 과 `forgen compound reopen <name>` 은 그 자체가 오너 승인이라 예외로 둔다(재관측 없이도 올릴 수 있다).
- 재추출로 은퇴 솔루션이 자동 복귀할 때는 은퇴 전 수준과 무관하게 candidate 로만 돌린다.
- 재관측 판정은 본문 유사도가 아니라 추출 모델의 이름 재사용으로 한다(실측: 이름 재사용 쌍 유사도 0.10·0.13, 무관 7,140쌍 상위 1% 0.074·최댓값 0.152 — 임계로 가를 수 없음). 0.8.0 이전 솔루션은 Context 의 러너 출처 표식으로 원래 세션을 되살린다.
