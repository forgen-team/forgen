## 1. 북극성

**forgen 은 내가 내린 결정에서 판단 기준을 배우고, 내가 무엇을 고를지 먼저 맞혀 보며, 맞히는 영역에서만 덜 묻는다. 그 기준은 내가 읽고 고칠 수 있는 글로 남아 어떤 모델로든 옮겨진다.**

### 지금과의 차이

| | 지금 (0.7.2) | 가려는 곳 |
|---|---|---|
| 무엇에서 배우나 | 교정 — 틀렸을 때 한 말 | 결정 전부 — 고른 것, 고르지 않은 것, 직접 쓴 답, 교정 |
| 무엇을 저장하나 | 문장 하나짜리 룰. 이유와 조건이 없다 | 목적·조건·우선순위가 붙은 판단 카드, 그 아래 원문 근거 |
| 잘 배웠는지 어떻게 아나 | 주입 횟수. 효과는 모른다 | 숨겨 둔 예측이 내 실제 선택과 맞은 비율 |
| 배운 것으로 무엇을 하나 | 매 세션 같은 글을 다시 읽힌다 | 맞히는 영역은 묻지 않고 진행한 뒤 보고, 못 맞히는 영역은 계속 묻는다 |
| 누가 쓴 것인가 | 직접 한 말과 모델이 추론한 것이 한 목록 | 내가 쓴 층과 모델이 쓴 층이 갈라져 있고, 모델 층은 승인 전엔 강제력이 없다 |

README 의 북극성("당신처럼 판단하는 Claude")은 그대로다. 빠져 있던 것은 **"당신처럼"을 재는 방법**과, 배우는 재료가 교정뿐이라는 점이다.

### 왜 지금인가 — 버려지고 있는 데이터

**집계 정의(이 문서의 모든 수치)**: 단위 = 질문 1개(한 번의 호출에 질문이 1~4개 든다). 범위 = 이 서버의 최상위 세션 기록만(서브에이전트 기록 제외 — 거기에는 이 도구 호출이 0건이다). 기간 = 2026-07-02T08:05Z ~ 2026-11-25T05:08Z(집계 시점까지. 세션 7개 중 2개는 7월, 1개는 10월, 4개는 11월에 시작). 중복 제거 = 도구 호출 ID, 같은 호출의 결과 줄이 여러 번 나오면 답이 든 것을 쓴다.

분류 규칙(위에서부터 먼저 맞는 것): ① 답 없음 ② **복수 선택** = 질문의 `multiSelect` 값이 참(답 문자열의 쉼표로 판별하지 않는다) ③ **직접 입력** = 답 문자열이 어느 선택지 라벨과도 같지 않음 ④ **추천 표시 없음** = 라벨에 추천 표시(`(추천)`·`(Recommended)`)가 든 선택지가 없음 ⑤ 고른 라벨이 추천 표시가 붙은 것이면 **추천 그대로**, 아니면 **다르게**. 추천 표시가 둘 이상 붙은 질문(6개)은 그중 하나를 고르면 그대로로 센다.

- 선택형 질문(AskUserQuestion) 호출 83건, 질문 164개, 답이 있는 것 162개(세션 7개) [데이터]. 이 중 139개가 11-12 이후 2주에 몰려 있다. 같은 시기 직접 교정은 11-05 이후 32건이다. **결정이 교정보다 많다.**
- 답 162개의 구성: 추천 그대로 85 · 추천과 다르게 15 · **선택지 밖 직접 입력 35** · 복수 선택 20 · 추천 표시 없음 7 [데이터]. 답 없음 2. 형식이 깨진 호출 2건은 질문 수에서 빠졌다.
- 추천 표시가 있는 질문은 137개이고 **137개 모두 첫 번째 선택지**에 붙어 있었다.
- 복수 선택 20개 중 답이 라벨만으로 이뤄진 것은 10개, 나머지는 라벨에 직접 쓴 말이 섞였다. `multiSelect` 가 아닌 질문에서 쉼표로 라벨을 이어 답한 경우는 0개다. 쉼표를 기준으로 복수 선택을 세면 직접 입력 속 쉼표 때문에 수가 흔들린다(비평자 집계에서 19~30).
- 집계는 시점에 민감하다. 같은 규칙으로 11-24 까지만 세면 호출 76 · 질문 145 · 그대로 72 · 다르게 11 · 직접 입력 35 · 복수 18 · 표시 없음 7 이다. 이 문서를 쓰는 동안에도 이 세션에서 답이 늘었다. 비평자 집계(호출 83 · 질문 164 는 일치, 그대로 73 · 다르게 14 · 직접 입력 31 · 표시 없음 13)와 남는 차이는 분류 규칙 차이로 보이며 맞춰 보지는 않았다 [미확인].
- 팀 리드의 앞선 집계(답 76건)와 이 문서 1판(답 114개, 그대로 55 · 다르게 8)이 적었던 이유: 같은 호출의 결과 줄이 기록에 두 번 이상 나오는 호출이 21건이고, 그중 답이 빠진 사본을 집으면 "답 없음"으로 세어진다(여기에 그 뒤 하루치 답이 더해졌다). 1판의 114 는 이 원인으로 확인했고, 리드 집계는 같은 원인일 것으로 본다 [유력]. 수집기는 이 중복을 반드시 다뤄야 한다.
- forgen 에 이 도구를 다루는 코드는 없다 [코드]. 호스트의 내장 도구라 forgen 이 정의한 것도 아니다. 선택지·고른 것·버린 것·직접 쓴 이유가 이미 있는데 쌓지 않는다.
- 이 기록은 호스트(Claude Code)의 대화 기록 파일에만 있고, 호스트는 오래 손대지 않은 파일을 지운다. 이 서버에 남은 최상위 기록 58개 중 가장 오래된 **수정 시각**은 2026-11-04 이고, 가장 오래된 **기록 내용**은 2026-07-02 다(이어 쓰인 세션이라 파일이 살아남았다) [데이터]. 다른 환경에서는 지워진 프로젝트 폴더가 1,178개였다(`next-version-plan.md` §11.1). 보관 기간 기본값은 1차 문서로 확인하지 않았다 [미확인]. **한번 지워진 세션의 결정은 복구할 수 없다** [유력].

## 3. 방향

팀 리드 가설 A~F 를 확인해 다듬었다. D 는 뒤로 미뤘고, F 는 B 에 합쳤고, E 는 "정확도"가 아니라 "어느 질문을 건너뛰어도 되는가"의 문제로 다시 정의했다.

### A. 결정 원장 — 교정만이 아니라 결정을 쌓는다

- **문제**: 배우는 재료가 "틀렸을 때 한 말"뿐이다. 맞았을 때의 선택, 여러 후보 중 고른 것, 선택지를 다 버리고 직접 쓴 답은 버려진다(§1). 교정은 무엇이 싫은지만 말하고, 결정은 무엇과 비교해 무엇을 골랐는지를 말한다.
- **하루 장면**: 오전에 모델이 범위를 묻는다 — 세 안 중 첫째가 추천. 오너는 셋 다 고르지 않고 한 줄을 직접 쓴다. 지금은 그 한 줄이 그 세션에서만 쓰이고 사라진다. 원장이 있으면 그날 저녁 `forgen status` 에 "오늘 결정 6건: 추천 수용 4, 다르게 1, 직접 입력 1"이 보이고, 직접 입력한 한 줄은 근거 원문으로 남는다. 오너가 따로 하는 일은 없다.
- **최소 설계**
  - 세션이 끝나 러너가 대화 기록을 읽을 때(이미 스트림으로 읽는다) 선택형 질문의 호출과 답 쌍을 **결정적으로** 뽑아 `me/decisions/` 에 한 줄씩 쓴다. 모델 호출 없음, 훅 의존 없음, 주기 실행(sweep)이 놓친 세션을 메운다.
  - 요약용 분류 함수(`transcript-summary.ts` 의 `classifyEntry`)를 넓히지 않는다. 같은 파일을 한 번 읽는 길에 **별도 추출 함수**를 건다 — 요약에 들어가는 내용(전송 범위)이 바뀌면 안 된다.
  - 한 건의 필드: 시각, 세션, 위치(`origin` — 0.8.0 S1 과 같은 형식), 질문, 보여 준 선택지 전부와 순서, 추천 표시가 붙은 선택지, 고른 것, 직접 입력 원문, 종류(`accept` / `override` / `free` / `multi` / `no-recommendation` / `unanswered`), 호스트.
  - 교정(`correction-record`)도 같은 원장에서 보이게 한다(저장은 지금 자리 그대로, 읽는 뷰만 합침).
  - 중단·권한 거부·산출물 재수정은 **사실로만** 적고 해석하지 않는다. ADR-013 이 이런 신호의 정밀도를 0.15% 미만으로 실측했다. 쓰임새가 증명되기 전에는 학습에 쓰지 않는다.
- **데이터**: 새 폴더 하나. 지워도 기존 동작에 영향 없다. 내보내기(`compound export`, `way export`)에 기본으로 넣지 않는다(§7).
- **검증**: 실제 대화 기록에서 뽑은 건수가 손으로 센 건수와 같다(이 서버: 호출 83, 답 있는 질문 162). 결과 줄이 중복된 호출 21건에서 답을 잃지 않는다. 같은 기록을 두 번 읽어도 중복이 없다. Codex 에 같은 종류의 질문 도구가 있는지는 [미확인].
- **실패 조건**: 4주 동안 새 결정이 주 5건 미만으로만 쌓이면(질문이 드문 사용 방식) 이 재료로는 배울 수 없다 — B·C 를 교정 중심으로 다시 설계한다.

### B. 판단 카드 — 낱개 룰을 목적·조건·우선순위로 묶는다 (가설 B + F)

- **문제**: 룰은 문장 하나라 이유와 조건이 없다. 그래서 조건 없이 충돌하는 쌍이 함께 활성이고("전부 직접 테스트" 대 "테스트를 돌리지 말 것", `next-version-plan.md` §11.1), 같은 뜻이 여러 개로 갈라지고, 활성 본문이 예산(7천 자)을 넘는다. 모델은 93개 문장 중 무엇이 무엇보다 먼저인지 모른다.
- **하루 장면**: 지금은 세션 시작에 수십 개의 "~하지 마라"가 한 덩어리로 들어온다. 카드가 되면 세션 시작에는 카드 제목과 한 줄(예: "검증 — 언제 돌리고 언제 돌리지 않는가")만 10개 안팎 들어오고, 그 일이 실제로 벌어질 때 해당 카드 본문("작업 중에는 …, 끝내기 전에는 …, 이유: …")이 한 번 들어온다. 주 1회 오너에게 "카드 초안 2건: 흩어진 룰 5개와 결정 3건을 묶었습니다. 근거 인용 포함"이 오고, 오너는 읽고 승인하거나 한 줄 고친다.
- **최소 설계**
  - 카드 = 글 한 장: **언제**(조건), **무엇을 우선하나**(A 보다 B), **왜**(이유), **예외**, 근거 목록(룰·결정·교정의 ID).
  - 이유에는 출처를 붙인다: `stated`(오너가 직접 쓴 말에서) / `inferred`(모델이 추정). 추정 이유는 오너가 확인하기 전까지 추정으로 표시하고, 90일(기본값) 안에 확인되지 않으면 카드에서 뺀다.
  - 3층: 1층 색인(항상 주입, 작게) · 2층 카드 본문(위치나 조건이 맞을 때 한 번) · 3층 원문 근거(필요할 때 조회). 0.8.0 S5 의 위치 전환 주입과 0.9 의 발동 조건이 2층의 전달 수단이다.
  - **저자 분리**: 내가 쓴 층 = 직접 교정, 직접 입력한 답, 승인한 카드. 모델이 쓴 층 = 추론 교정, 카드 초안. 모델 층은 승인 전엔 색인에 오르지 않고 차단에 쓰이지 않는다. 승인은 0.8.0 의 솔루션 승인과 **같은 묶음 한 곳**에서 한다.
  - 카드는 0.9 "정리(꿈꾸기)"의 산출 형식이다. 정리 기능을 따로 만들고 카드를 또 만드는 것이 아니다. 원본 룰은 지우지 않고 카드가 그 룰들을 대표한다(되돌리면 룰이 다시 낱개로 주입된다).
  - 내보내기는 ADR-020 의 `compile()` 이 카드를 항목 종류 하나로 받도록 확장한다. 카드는 처음부터 글이라 다른 모델로 옮기기에 룰보다 낫다.
- **데이터**: `me/cards/*.md`(frontmatter + 본문). 룰에 선택 필드 `card`(대표 카드 ID).
- **검증**: (1) 같은 룰 집합에서 주입 글자 수가 줄고 hard·안전 룰 누락 0. (2) 카드의 모든 근거 ID 가 실재하고 인용이 원문에 있다(기계 검사). (3) §3 C 의 예측 정확도가 낱개 룰일 때보다 떨어지지 않는다.
- **실패 조건**: 오너가 초안의 절반 이상을 고쳐 써야 하면 카드 작성이 새 일거리가 된 것이다 — 초안 생성을 멈추고 "같은 뜻 병합"만 남긴다. C 에서 카드가 낱개 룰보다 못하면 형식을 버린다.

### C. 예측 채점 — "나처럼 판단하는가"를 직접 잰다

- **문제**: 지금 지표(주입 횟수, 차단 수)는 forgen 이 한 일을 세지 결과를 세지 않는다. 0.8.0 의 교정 3분류는 "같은 교정이 되풀이되는가"를 재지만 틀렸을 때만 본다.
- **하루 장면**: 오너에게 보이는 변화는 `forgen status` 한 줄이다 — "지난 4주 결정 41건 중 예측 일치 31. 추천을 그대로 받은 경우 28/30, 추천과 달랐던 경우 3/11". 둘째 숫자가 오르는지가 forgen 이 오너를 배우고 있는지의 답이다.
- **최소 설계**
  - **과거 결정 재생(오프라인)**: 원장의 결정을 과제로 쓴다. 추천 표시를 지우고 선택지 순서를 섞은 뒤, (가) 카드·룰 없이 (나) 그 결정 **이전에** 있던 카드·룰만 주고 모델에게 "이 사람은 무엇을 고를까"를 묻는다. (나)−(가)가 배운 것의 값이다. `next-version-plan.md` §6 의 L2(교정 재생 비교)와 같은 틀이고 같은 실행기에 얹는다.
  - **두 숫자를 따로 낸다**: 추천을 받아들인 결정과, 추천과 다르게 고르거나 직접 쓴 결정. 앞쪽은 닻 효과로 쉽게 맞는다. 의미 있는 것은 뒤쪽이다.
  - 직접 입력한 답은 "선택지 중에 답이 없다"를 맞혔는지로 채점한다(문장 내용 채점은 하지 않는다).
  - 사전 등록: 과제 선정 기준·채점 방법·합격선을 돌리기 전에 고정한다. 표본 30건 미만이면 "판정 불가".
  - **비용**: 교정 재생 비교와 같은 크기다 — 과제 30 × 2조건 × 3회 = 본 모델 호출 180회(`next-version-plan.md` §6.3·§8 Q3). 두 비교를 함께 돌리면 360회. Haiku 가 아니라 본 모델이라 자주 돌릴 수 없다(버전당 1회 기준).
  - **표본이 언제 차나**: 필요한 것은 추천과 달랐던 답 30건이다. 지금 15건이고 전부 11-12 이후 2주에 나왔다(하루 1건꼴). 같은 속도면 2주쯤 더, 직접 입력(35건)을 포함하면 이미 넘는다. 다만 이 2주는 계획·설계 결정이 몰린 시기라 평소 속도는 모른다. 절반으로 떨어져도 한 달 남짓이므로 0.10 배치와 맞는다. 0.10 시점에 30건이 안 되면 "판정 불가"로 보고한다.
  - **다른 모델로 옮겨도 통하나**: 같은 카드를 주고 모델별로 같은 과제를 채점한다. "어떤 모델로든 옮겨진다"는 북극성의 검증이다(비용이 모델 수만큼 늘어 1.0 직전에 1회).
- **데이터**: `state/metrics/prediction/` 에 회차별 결과. 원장은 읽기만.
- **검증**: 채점기가 정답을 보지 못한다는 것(추천 표시 제거, 순서 섞기)을 픽스처로 확인. 시간 순서 위반(나중 카드로 앞선 결정을 맞히기) 0건.
- **실패 조건**: 추천과 달랐던 결정에서 (나)가 (가)를 넘지 못하면, 쌓은 카드·룰은 오너의 판단을 담고 있지 않은 것이다. 그 결과를 그대로 공개하고 E 는 시작하지 않는다. 그리고 B 를 다시 설계한다 — 룰 묶음에서 출발하지 않고 직접 입력과 추천을 뒤집은 결정을 근거로 카드를 쓴다.
- **예비 확인과 한계**: §4.

### D. 워크플로우 승격 — 뒤로 미룬다

- **문제**: 승격된 스킬 0개. 반복되는 일의 순서가 스킬이 되지 않는다.
- **판단**: 방향은 맞지만 지금 할 일이 아니다. 스킬의 원료는 검증된 솔루션과 카드인데 둘 다 아직 0 이다(솔루션 검증 0건, `next-version-plan.md` §2.2). 원료 없이 순서만 캐면 "자주 하는 것"을 "잘하는 방법"으로 착각한다 — 재관측을 검증으로 착각하는 것과 같은 오류다.
- **최소 설계(나중)**: 승인된 카드와 검증된 솔루션이 같은 작업 흐름에 3개 이상 묶이면 스킬 초안을 제안한다. 오너 승인 후에만 `SKILL.md` 가 된다. 기존 `skill promote` 경로를 쓴다.
- **하루 장면(나중)**: 릴리스를 세 번째 할 때 "지난 두 번 이 순서로 했고 두 번 다 같은 지점에서 고치셨습니다. 절차 초안을 볼까요?"가 한 번 뜬다.
- **실패 조건**: 승인된 스킬이 4주 안에 한 번도 호출되지 않으면 제안 기준이 틀린 것이다.

### E. 위임 사다리 — "건너뛰어도 되는 질문"을 가린다

- **문제를 다시 정의한다**: 답 162개 중 85개는 추천을 그대로 받은 것이다. 이 질문들은 오너의 시간을 썼지만 결과를 바꾸지 않았다. 반대로 50개(다르게 15 + 직접 입력 35)는 묻지 않았다면 틀렸을 수 있는 것이다(직접 입력 중 추천안을 보충만 한 것이 얼마인지는 분류하지 않아 모른다 — 상한이다). 그러니 필요한 능력은 "오너의 답을 맞히기"보다 **"이 질문은 추천대로 갈 것이다"를 높은 확신으로 가려내기**다. 전부 안 물으면 많게는 3번에 1번꼴로 틀리고, 전부 물으면 절반은 결과를 바꾸지 않는 질문이다.
- **하루 장면**: 지금은 하루 열 번 묻고 그중 여덟아홉은 첫 번째를 누른다. 사다리 2단에서는 되돌릴 수 있는 선택 중 지난 기록이 충분한 종류는 묻지 않고 진행한 뒤 응답 끝에 "이렇게 정했습니다(근거 카드: …). 다르면 말씀해 주세요"를 한 줄 남긴다. 배포·삭제·결제·외부 발송은 예전처럼 항상 묻는다.
- **최소 설계**
  - 0단: 지금처럼 묻는다.
  - 1단(그림자): 묻되, 물을 필요가 있었는지 사후에 기록한다. C 의 채점에서 "건너뛰었다면 틀렸을 비율"을 영역별로 낸다.
  - 2단: 한 영역에서 결정 20건 이상이 쌓이고 그림자 기록의 틀릴 비율이 정한 값(예: 5%) 이하이면, 그 영역의 **되돌릴 수 있는** 선택만 진행 후 보고. 한 번 뒤집히면 그 영역은 1단으로 내려간다.
  - 되돌리기 어려운 일과 바깥으로 나가는 일은 단계와 무관하게 항상 사람.
  - 모델 자신의 판단이 예측된 오너 선택과 다르면 숨기지 않고 둘 다 말한다("보통은 A 를 고르시지만 이번엔 B 가 낫다고 봅니다. 이유 …"). 과거 선택을 따라가기만 하지 않기 위한 장치다.
- **데이터**: 카드에 영역별 단계와 근거 건수. 진행 후 보고 건마다 원장에 `auto` 로 기록(나중에 뒤집혔는지 포함).
- **검증**: 2단에서 뒤집힌 비율이 그림자 기록의 예측과 맞는가. 되돌리기 어려운 범주가 자동 진행된 건 0.
- **실패 조건**: 2단 영역에서 뒤집힘이 정한 값의 두 배를 넘으면 전체를 1단으로 되돌린다. 오너가 "왜 안 물었냐"고 교정하면 그 교정이 최우선 근거다.

## 4. 예비 확인 — 지금 가진 기록으로 본 C

대상: 단일 선택이고 추천 표시가 있던 답 100개(§1 의 집계 정의와 기간, 세션 5개, 선택지 2개 40 · 3개 53 · 4개 7). 스크립트 집계, 모델 호출 없음.

| 예측 방법 | 맞은 수 / 100 | 추천과 달랐던 15개 중 |
|---|---|---|
| 무작위(선택지 수 기준 기댓값) | 39.4 | — |
| 지금 있는 직접 교정 룰과 낱말이 가장 많이 겹치는 선택지 (그 결정 이전에 만들어진 룰만, 88개 대상) | 64 | 4 |
| 항상 추천을 고른다 = 항상 첫 번째를 고른다 | 85 | 0 |

읽는 법과 한계:
1. **닻과 위치가 완전히 겹친다.** 추천은 100개 전부 첫 번째 자리에 있었다. 85% 가 "추천이 옳았다"인지 "첫 번째를 눌렀다"인지 "추천이라고 써 있었다"인지 이 기록으로는 가를 수 없다.
2. 낱말 겹침 예측은 무작위(39%)보다 높고(64%) 닻 기준선(85%)에는 못 미친다. 룰 글에 선택과 닿는 정보가 조금은 있다는 정도까지만 말할 수 있다. 의미를 보지 않는 조잡한 방법이라 "룰이 판단을 담고 있지 않다"는 결론도 내릴 수 없다.
3. 추천과 달랐던 답은 15개다. 이 수로는 어떤 방법의 우열도 가릴 수 없다(4/15 는 선택지 2~4개에서의 우연과 구분되지 않는다).
4. 그래도 설계에 주는 것은 분명하다.
   - 판단 예측은 **"항상 추천"(85%)을 이겨야** 의미가 있고, 그 차이는 추천과 달랐던 답과 직접 입력에서만 나올 수 있다.
   - 직접 입력이 35개(답의 22%)로 추천과 다르게 고른 것의 두 배가 넘는다. "선택지가 틀렸다"는 신호이자 오너 자신의 말이라 가장 값진 재료다. (추천안을 보충한 것인지 뒤집은 것인지는 본문을 분류하지 않아 모른다.)
   - 추천이 늘 첫 자리에 오는 한, 앞으로 쌓이는 기록도 같은 한계를 갖는다 → §9 Q2.

### 4.1 닻 없는 표본을 만드는 방법 (Q2 의 (b))

- 선택형 질문은 호스트 내장 도구라 forgen 이 질문을 직접 만들지 않는다. 손댈 수 있는 자리는 PreToolUse 훅뿐이다: 도구 이름이 `AskUserQuestion` 인 호출을 보면 `updatedInput` 으로 `options` 순서를 섞고 추천 표시를 뗀 입력을 돌려준다. 원래 순서와 추천은 원장에 따로 적는다.
- **실측 범위**: `updatedInput` 이 입력을 바꾸는 것은 MCP 도구인 `correction-record` 에서만 확인했다(Linux·macOS, `next-version-plan.md` §4.3·§11.2). 내장 도구인 `AskUserQuestion` 에 훅이 오는지, 바뀐 `options` 가 화면에 그대로 뜨는지, 답이 바뀐 라벨 기준으로 돌아오는지는 **실행해 보지 않았다 [미확인]**. Codex 는 전부 미확인. 안 되면 (b)는 불가능하고 채점은 "추천과 달랐던 답"에서만 주장한다.
- 다른 훅이 같은 입력을 바꾸면 하나만 남는다(§11.2 관찰). 여러 훅 공존에 기대지 않는다.
- 되돌릴 수 있는 선택에만 적용하고, 섞은 질문임을 오너가 알 수 있게 머리말에 표시를 남긴다(몰래 바꾸지 않는다).

## 5. 우선순위와 배치

| 버전 | 이 문서의 몫 | 근거 |
|---|---|---|
| 0.8.0 | **A 의 수집만**: 러너가 선택형 질문과 답을 원장에 적는다 + 업그레이드 때 남아 있는 대화 기록에서 1회 소급 수집. 주입·동작 변화 없음, `status` 에 건수 한 줄 | 호스트가 대화 기록을 지우므로 나중에 복구할 수 없다(§1). 러너가 이미 같은 파일을 읽으므로 추가 경로가 없다. 0.8.0 의 `origin` 형식을 그대로 쓴다 |
| 0.9 | **B**: 정리(꿈꾸기)의 산출을 카드 초안으로. 승인 묶음을 솔루션 승인과 한 곳으로. 3층 주입. 원장 뷰에 교정 합치기 | 0.9 의 정리·발동 조건과 같은 일이다. M3·M4 결과가 전제 |
| 0.10 | **C**: 과거 결정 재생 채점을 교정 재생 비교(L2)와 같은 실행기로. **E 1단**(그림자 기록) | 원장이 4주 이상 쌓여야 표본이 된다 |
| 1.0 | 조건 추가: 예측 채점 결과를 공개한다(효과가 없으면 없다고). **E 2단은 1.0 조건이 아니다** — 1.0 뒤 오너 결정 | "답이 있음"이 조건이라는 기존 원칙과 같다 |
| 그 뒤 | D(워크플로우 승격), E 2단 | 원료(검증된 솔루션·승인된 카드)가 쌓인 뒤 |

0.8.0 에 넣는 것은 A 의 수집 하나뿐이다. 0.8.0 은 이미 범위가 크고(S·K·M), 카드·채점·위임은 0.8.0 의 수리(범위, 출처 표시, 계측) 위에 서야 한다. 수집만은 미루면 재료가 사라진다.

구현 전 확인할 것: 호스트의 대화 기록 보관 기간 설정(이 서버 설정 파일에는 값이 없다 — 기본값이 적용 중인 것으로 보이나 1차 문서로 확인하지 않음 [미확인]), Codex 의 질문 도구 유무, 집계 단위(호출/질문/답) 고정.

## 6. 설계 원칙 — forgen 이 일을 늘리지 않게

오너가 지목한 글의 경고("기존 흐름에 AI 를 얹으면 일이 늘어난다")는 forgen 자신에게 먼저 해당한다. 0.8.0 만으로도 오너에게 가는 검토가 넷이다(룰 검토, 범위 검토, 솔루션 승인, 미정 범위). 카드 승인이 다섯째가 되면 forgen 이 일거리가 된다.

1. **승인함은 하나**. 룰·범위·솔루션·카드를 한 묶음으로, 하루 한 번을 넘지 않게, 한 번에 5건 이하.
2. **오너에게 글을 쓰게 하지 않는다**. 이유는 오너가 이미 쓴 말(직접 입력, 교정)에서만 가져오고, 따로 설문하지 않는다.
3. **forgen 에 쓴 시간을 잰다**. 승인·검토에 쓴 건수와 대기 일수를 `status` 에 보인다. 줄인 질문 수(E)보다 늘린 검토 수가 많으면 방향이 틀린 것이다.
4. **수집은 조용히, 사용은 승인 뒤에**. 원장에 쌓이는 것만으로는 아무 동작도 바뀌지 않는다.

## 7. 위험

| 위험 | 내용 | 대비 |
|---|---|---|
| 사생활·회사 자료 | 질문과 선택지에는 작업 내용이 그대로 들어 있다. 회사 기기의 결정에는 회사 정보가 섞인다 | 원장은 기기 밖으로 나가지 않는다: 내보내기 기본 제외, 기기 간 동기화 없음. 프로젝트별 수집 끄기(0.8.0 키 등록부에 설정). 기존 비밀 마스킹과 `<private>` 제외를 그대로 적용. 카드 초안을 만들 때 모델에 보내는 것은 지금 추출과 같은 신뢰 경계이지만 보내는 내용이 늘어나므로 첫 실행 안내를 갱신한다. 공개 문서·저장소에는 건수만 |
| 아첨 | 오너 취향을 맞추는 것과 오너가 틀려도 맞다고 하는 것은 다르다 | 카드는 선호와 트레이드오프에만 쓴다. 사실 확인이 필요한 판단에서 카드는 근거가 될 수 없다고 카드 머리말에 적는다. 모델 판단이 예측과 다르면 둘 다 말하게 한다(§3 E) |
| 자기 강화 | 결정의 다수는 모델 추천을 받아들인 것이다. 이를 "오너의 판단"으로 배우면 모델이 자기 추천을 다시 배운다 | 수용은 약한 근거, 다르게 고른 것과 직접 입력은 강한 근거로 따로 센다. 수용만으로는 카드를 만들지 않는다. 채점도 둘을 나눠 낸다. **추천 수용 비율의 4주 추이**를 `status` 에 보인다 — 카드가 늘면서 수용 비율만 오르고 닻 없는 표본의 일치는 그대로면 모델이 자기 추천을 되먹이고 있다는 신호다 |
| 과적합 | 표본이 작다(다르게 고른 답 15개). 한 세션의 버릇이 성향으로 굳는다 | 서로 다른 세션 2곳 이상의 근거가 있어야 카드 후보. 시간 순서로 나눠 앞의 기록으로 만든 카드를 뒤의 결정으로 채점. 영역별 최소 건수 미만은 "판정 불가" |
| 굳어짐 | 취향은 바뀐다. 옛 선택이 정체성처럼 남는다 | 카드에 마지막 확인 날짜. 최근 결정이 카드와 어긋나면 카드를 검토함에 올린다. 오래 확인되지 않은 카드는 색인에서 내려간다 |
| 통제권 | 무엇이 쌓였고 어디에 쓰이는지 못 보면 감시가 된다 | `forgen decisions` 로 목록·삭제. 카드는 사람이 읽는 글이고 근거 링크로 원문까지 내려간다. 지우면 그 근거에 기댄 카드가 표시된다 |
| 위임 사고 | 묻지 않고 진행한 것이 틀림 | 되돌릴 수 있는 것만, 영역별로, 한 번 뒤집히면 강등. 되돌리기 어려운 범주는 코드에 고정된 목록으로 항상 사람 |
| 닻에 묶인 정답 | 추천을 먼저 본 답은 오너의 독립된 판단이 아니다 | §9 Q2·§4.1. 못 풀면 채점은 "추천과 달랐던 답"에서만 주장한다 |

## 8. 하지 않을 것

- "100% 복제"를 목표나 문구로 쓰기
- 음성·화면 상시 녹화, 클릭·체류 같은 암묵 신호로 성향 추정
- 오너에게 이유를 묻는 설문, 결정마다 확신 정도 입력 요구
- 중단·권한 거부를 교정으로 해석해 룰 만들기(ADR-013 유지)
- 범용 개인 지식 위키, 벡터 DB, 지식 그래프
- 모델이 쓴 이유를 오너의 이유로 저장
- 원장을 다른 기기·다른 사람과 공유, 팀용 기능
- 예측이 맞는다는 이유만으로 되돌리기 어려운 일을 자동 진행
- 카드·채점·위임을 0.8.0 에 넣기
- 채점 결과가 나쁠 때 지표를 바꾸기
