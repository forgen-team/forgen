## 0. 결론 먼저

1. **오너 판단이 맞다.** "교정을 잡아 기억하고 다음 세션에 넣어 준다"는 forgen 의 원래 핵심은 이제 Claude Code 기본 기능이다. 공식 문서가 자동 메모리를 "사용자의 교정과 선호를 바탕으로 Claude 가 스스로 쓰는 메모"라고 설명하고, 메모 종류에 `feedback`(교정)이 따로 있다 [문서]. 경로별 룰(`.claude/rules` 의 `paths:`), 조직 정책용 관리형 CLAUDE.md, 34개 훅 이벤트, 모델이 판정하는 훅(`type: prompt/agent`)도 있다 [문서]. Codex 는 로컬 메모리와 통합(consolidation)을, Cursor 는 대화에서 뽑는 메모리와 강제할 수 있는 팀 룰을 갖췄다 [문서/2차].
2. **호스트가 안 하는 것은 "그 기억이 실제로 먹혔는지 재는 일"과 "틀린 기억을 원문과 대조해 바로잡는 일"이다.** 호스트 문서 스스로 "CLAUDE.md 와 메모리는 맥락일 뿐 강제 설정이 아니다", "두 지시가 부딪히면 Claude 가 아무거나 고를 수 있다"고 쓴다 [문서]. Anthropic 의 메모리 연구도 "틀린 메모는 다음 세션으로 퍼지고, 검증 빈도와 비용은 풀리지 않은 문제"라고 적었다 [원문]. 사용자들이 메모리 도구를 안 쓰는 이유 1·2위도 "안에 뭐가 들었는지 보고 고칠 수 없다", "쌓일수록 중복·모순이 생긴다"였다 [원문].
3. **추천 방향: "에이전트 기억 감사관"** — 호스트들이 이미 쌓고 있는 기억(CLAUDE.md, 자동 메모리, `.claude/rules`, AGENTS.md, Codex 메모리)을 대신 만들지 말고, **읽어서 검사하고, 효과를 재고, 근거와 함께 고칠 안을 내는** 로컬 도구로 간다. forgen 이 가진 가장 남다른 자산(대화 기록 재생, 같은 교정 재발 측정, 차단 영수증과 룰별 정밀도, "효과 없음"도 공개하는 측정 습관)이 그대로 쓰인다.
4. **결정 학습(`direction.md`)은 버리지 않고 이 감사관의 두 번째 단계로 넣는다.** "내 기억이 내 판단을 맞히는가"는 감사의 가장 강한 형태다. 다만 단독 제품으로는 시장 근거가 약하다(§3, §4 방향 B).
5. **버릴 것**: forgen 자체 룰 저장소를 "주 기억"으로 키우는 일, 매 세션 대량 주입, 완료 주장 가드를 대표 기능으로 내세우는 일, 범용 솔루션 회수 경쟁, 세션 관리·상태 표시줄 같은 붐비는 부가 기능(§5).

### 2.8 트렌드에서 읽히는 것

- **돈·시간이 새는 곳은 "기억이 없어서"가 아니라 "기억을 믿을 수 없어서"로 옮겨 갔다.** 1년 전 아픔(세션마다 잊는다)은 호스트가 풀었다. 지금 아픔은 틀린 메모의 전파(T1), 보이지 않음(T2), 중복·모순(T2, T30), 길어지면 안 지킴(T7, T14), 실제로 로드됐는지 모름(T32)이다.
- **하네스를 더 얹는 쪽은 역풍이다**(T27~T29). 새 도구는 "더 넣는" 것이 아니라 "빼고 줄이고 확인하는" 쪽이어야 받아들여진다.
- **팀 거버넌스는 호스트와 대형 업체의 영역이 됐다**(T26, 관리형 설정, Cursor 강제 팀 룰). 1인 오픈소스가 들어갈 자리는 거의 없다.
- **이식성은 AGENTS.md 로 수렴**하고 있다(T31, T33). 형식 변환만으로는 가치가 줄어든다.
- **데이터 불신**(T25, T34)은 "로컬 전용"을 실제 장점으로 만든다.

## 4. forgen 이 갈 수 있는 특수한 방향

### 방향 A. 에이전트 기억 감사관 — "Claude 가 기억한 것이 맞는지, 먹히는지 잰다" (추천)

- **한 줄**: 호스트들이 쌓는 기억(CLAUDE.md·`.claude/rules`·자동 메모리·AGENTS.md·Codex 메모리)을 읽어 **부딪힘·중복·낡음·잘림·다른 프로젝트 섞임**을 찾고, 대화 기록을 재생해 **"이 기억이 생긴 뒤 같은 교정이 줄었는가"**를 재고, 원문 인용이 붙은 수정안을 낸다. 고치는 것은 사람이 승인.
- **누가 왜**: 몇 달째 같은 저장소에서 Claude Code·Codex 를 쓰는 개발자. 사람 시간의 13%가 교정, 3%가 같은 규칙 다시 말하기(T9). 메모리 도구를 안 쓰는 이유가 "못 보고 못 고쳐서"(T2). 지침이 길어지면 안 지키고(T7, T14), 틀린 메모가 계속 퍼진다(T1).
- **호스트가 따라오기 어려운 이유**: (1) 호스트는 자기 메모리의 **정직한 효과 측정**을 공개할 유인이 약하다 — 숫자가 나쁘면 자기 제품이 나빠 보인다. (2) 여러 호스트의 기억을 **한자리에서** 비교하는 일은 각 호스트가 하지 않는다. (3) "효과 없음"까지 공개하는 측정 문화는 forgen 이 이미 실행해 온 것이다(honest-null).
- **금방 따라올 위험**: 높다. Auto Dream 이 중복·모순 정리를 이미 하고(보도), `/memory` 화면에 경고 몇 줄만 붙어도 "기본 기능"이 된다. **방어선은 정리 자체가 아니라 '재발 측정'과 '교차 호스트'다.** 정리 기능만 만들면 1년 안에 겹친다.
- **재사용 자산**: 대화 기록 스트림 읽기와 재생(`v1.0-plan.md` §3.3), 같은 교정 재발 측정(숫자 1), 범위 등록부(0.8.0 S3), `rule merge-mined`, `way collect-memory`, `way export` 8종(수정안을 각 호스트 형식으로 되돌려 쓰기), 차단 영수증·룰별 정밀도, 예산·잘림 계산(숫자 3).
- **증명할 숫자**: ① 감사가 찾은 문제 중 사람이 "맞다"고 한 비율(정밀도, 목표 70%+) ② 감사 후 4주간 같은 교정 재발률 변화(감사 전 재생 기준값 대비) ③ 상시 로드 글자 수 감소량과 그동안 중요 지침 누락 0 ④ 외부 설치자 수와 "감사 결과 받아들임" 비율.
- **첫 버전 범위**: `forgen audit` 한 명령. 읽기 전용. Claude Code 만. 다섯 가지 검사: 부딪히는 지시 쌍, 같은 뜻 중복, `MEMORY.md` 200줄·25KB 넘어 잘린 항목, 다른 프로젝트 이야기가 섞인 전역 지침, 최근 30일 대화에서 **이미 적혀 있는데도 다시 나온 교정**(= 적어 둔 기억이 안 먹힌 증거). 결과는 원문 인용 붙은 한 페이지. 모델 호출은 Haiku 로 같은 뜻 판정에만, 기기 밖 전송 없음(기존 원칙). 쓰기·차단·주입 없음.

### 방향 B. 판단 대리 — 결정 원장과 위임 사다리 (`direction.md`)

- **한 줄**: 선택형 질문의 답을 쌓아 "이 사람은 무엇을 고를까"를 숨긴 채 맞혀 보고, 맞히는 영역은 묻지 않고 진행 뒤 보고.
- **누가 왜**: 세션 여러 개를 돌리며 결정 요청에 시간을 쓰는 사람(T10). 진행 확인 9.5%·재촉 4%(T9).
- **호스트가 따라오기 어려운 이유**: 사람별 누적 학습과 정확도 공개는 호스트가 안 한다. **위험**: 호스트는 이미 다음 메시지를 예측한다(메시지 제안). 사람별로 개인화하는 것은 호스트에겐 작은 한 걸음이다. Auto mode 가 "묻지 않고 진행"의 상당 부분을 이미 가져갔다.
- **재사용 자산**: 결정 원장 설계, 교정 재생 실행기, 사전 등록·표본 하한 규칙.
- **증명할 숫자**: 추천과 다르게 고른 결정에서의 예측 일치(기록 있음 대 없음), 숨은 추천 일치율(v1.0 숫자 4b).
- **솔직한 평가**: 기술적으로는 가장 독특하다. 그러나 (1) 원료가 호스트의 선택형 질문 도구에 달려 있고 Codex 는 [미확인], (2) 오너 한 명의 결정 162개로 설계됐고 외부 수요 신호가 거의 없다(ALIGNS.md 반응 미미), (3) 표본이 차는 데 한 달 이상. **단독 제품이 아니라 A 의 두 번째 단계로**("내 기억이 내 판단을 맞히는가") 두는 것이 맞다.

### 방향 C. 교차 호스트 기억 번역기 — 로컬 우선

- **한 줄**: 하나의 원본에서 CLAUDE.md·`.claude/rules`(paths 포함)·AGENTS.md·`.cursor/rules`·Codex 설정으로 내보내고, 서로 어긋나면 알려 준다.
- **누가 왜**: 에이전트를 섞어 쓰며 규칙을 반복 설명하는 사람(T9 "규칙이 에이전트 사이에 안 넘어감"). 외부 서버형(Heirmos)이 싫은 사람.
- **호스트가 따라오기 어려운 이유**: 호스트끼리 경쟁 관계라 서로의 형식을 챙겨 주지 않는다. **위험**: AGENTS.md 수렴(T31)으로 필요가 빠르게 준다. 형식 변환은 해자가 얕다.
- **재사용 자산**: `way export`/`way import` 거의 그대로.
- **증명할 숫자**: 호스트를 바꿨을 때 같은 교정 재발(바꾸기 전 대비).
- **솔직한 평가**: **기능으로는 쓸모, 제품으로는 약하다.** A 의 출력 단계(수정안을 각 호스트에 써 넣기)로 흡수.

### 방향 D. 팀 규칙 준수 영수증

- **한 줄**: 팀 지침(ADR·AGENTS.md)이 세션마다 실제로 지켜졌는지 근거와 함께 남기는 기록, PR 에 붙는 준수 보고.
- **누가 왜**: 규칙 준수가 엄격 기준 36% 미만이고 "지켰다고 거짓 보고"까지 하는 상황(T14), ADR 근거로만 차단 사유를 다는 리뷰(T11), 늘어나는 팀 에이전트 관리(T23). 돈을 내는 곳은 여기다.
- **호스트가 따라오기 어려운 이유**: 거의 없다. 관리형 설정·승인 정책·PR 리뷰·관리자 플러그인을 호스트가 직접 내고 있다(T26, §1.1). 기업 판매에는 영업·보안 심사·지원 인력이 필요하다.
- **재사용 자산**: 차단 영수증, 룰별 정밀도, Stop 훅 판정.
- **솔직한 평가**: **지금의 forgen(1인 유지, 외부 사용자 0)으로는 가망이 낮다.** 시장은 크지만 들어갈 길이 없다. A 가 개인 사용자에게 통한 뒤에야 검토할 일.

### 방향 E. 완료 주장·검증 가드 강화

- **솔직한 평가**: **가망 없다.** 최신 모델에서 forgen 자체 측정으로 차단 0, 호스트가 `/verify`·`type: prompt` Stop 훅·PR 리뷰를 직접 준다. 남길 것은 가벼운 안전망 정도.

## 5. 추천과 버릴 것

### 추천: 방향 A "에이전트 기억 감사관"

이유:
1. **호스트와 싸우지 않고 호스트 위에 선다.** 호스트가 기억을 더 많이 쌓을수록 감사할 거리가 늘어난다. "하네스를 더 얹는 쪽"이 아니라 "빼고 줄이고 확인하는 쪽"이라 지금의 하네스 피로(T27~T29)와 같은 방향이다.
2. **사람들이 말한 아픔과 정확히 맞는다**: 보고 고칠 수 없음, 중복·모순, 틀린 메모 전파, 길면 안 지킴, 로드됐는지 모름(T1, T2, T7, T14, T32).
3. **forgen 이 이미 가진 것 중 남다른 것만 쓴다**: 재생, 재발 측정, 정직한 null 공개, 로컬 전용. 겹치는 자산(저장·주입)은 쓰지 않는다.
4. **첫 버전이 작고 읽기 전용이라 위험이 낮다**: 쓰기·차단이 없으니 사용자 환경을 망가뜨릴 일이 없고, 30초 안에 "내 CLAUDE.md 에 부딪히는 지시 2쌍, 이미 적혀 있는데 또 나온 교정 5건"이 보인다 — claude-mem 이 성공한 "설치 즉시 보이는 변화"를 감사 쪽에서 만든다.
5. **결정 학습(B)과 이식(C)을 버리지 않고 단계로 품는다**: 1단계 정리·재발 감사 → 2단계 "이 기억이 내 판단을 맞히는가" → 3단계 고친 결과를 각 호스트에 써 넣기.

주의할 점(정직하게):
- 정리 기능만으로는 1년 안에 호스트와 겹친다. **재발 측정과 교차 호스트 비교가 빠지면 이 방향도 없다.**
- 외부 사용자 0 에서 출발한다. 첫 버전의 성공 조건은 기능 수가 아니라 "오너 말고 한 사람이 써서 수정안을 하나라도 받아들였다"이다.
- 감사 판정에 모델(Haiku)을 쓰면 그 판정의 정밀도부터 사람 표본으로 재야 한다(기존 원칙 그대로).

## 6. 오너가 정할 것

1. 방향 A 를 forgen 의 새 중심으로 둘지(대안: B 단독, 또는 지금 계획(1.0 숫자 4개) 유지).
2. A 로 간다면 `v1.0-plan.md` 의 숫자 4개 중 무엇을 남길지. 제안: 숫자 1(같은 교정 재발)은 A 의 핵심 지표로 남기고, 숫자 2(회수)는 축소, 숫자 3(룰 섞임·탈락)은 "호스트 기억 감사" 항목으로 바꾸고, 숫자 4(결정)는 2단계로.

4. 기존 저장·주입 기능을 언제까지 유지할지(제안: 동결하고 새 기능을 얹지 않음, 사용자가 호스트 메모리로 옮기는 내보내기 제공).
